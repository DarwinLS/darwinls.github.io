Veraflux · Engineering

How Veraflux is built

Veraflux turns PubMed studies into cited supplement reports for a given age group, sex, and goal. I designed and built it end to end, from the React front end to the Python pipeline and the infrastructure under both.

Pre-launch, with no real traffic yet. The numbers on this page are measurements of the system itself.

Overview

In short

A React and TypeScript client is served by a Node and Express API, which calls a private Python and FastAPI service for retrieval and model work. They deploy as two Railway services on PostgreSQL, each with a staging copy on its own database, and Stripe handles subscriptions. The server runs as a single instance today.

  • A retrieval pipeline over PubMed with 13 model stages across Gemini and Claude, where the server removes any citation to a study the model wasn't given.
  • Request deadlines and load shedding in front of a backend that takes minutes, placed so an overloaded or stale request never spends quota or money.
  • Two database problems found and fixed before launch, including a production schema that couldn't be rebuilt from its migrations.

Applied AI · Retrieval

A report pipeline that cites only what it was given

A report starts with retrieval. The pipeline screens and profiles the supplement, generates and validates search synonyms, and then runs two branches in parallel. The efficacy branch sends 7 to 12 faceted PubMed searches for the goal, and the safety branch runs its own. Together the candidate pool can reach several hundred studies. The sample report above scanned 229. Selector models keep about 35 per branch, and synthesis writes from those. Safety analysis is cached as its own report, so reports on the same supplement can share it.

What the citation check guarantees

Citations are attached per paragraph as study IDs. Before a report is saved, a deterministic check removes any cited ID that wasn't in the set of studies the model was given, and the executive summary rejects anything shaped like a PMID or a year. So every citation points to a study the model was given. That still doesn't prove a study supports its sentence, and every citation links to its paper so a reader can check. Safety notes drawn from general pharmacology are labeled as such.

What it costs to run

Cost shaped the design around it. Every model call records its tokens and cost, and on the one day checked, the computed Anthropic cost matched the invoice exactly. Label scanning reads a photographed Supplement Facts panel in one vision call, then writes a short cited brief per ingredient, which costs about a twenty-fourth of a full report and is cached for every user. Free reports are generated for one fixed research cohort on 33 supplements across 5 goals, so there can only ever be 165 distinct free reports in the cache, however many people sign up.

Reliability

Deadlines and load shedding in front of a slow backend

A report can take minutes, so every route has its own budget: 360 seconds for a full report, 240 for safety and stack analysis, 120 for a brief, all under a 420-second socket limit. The pipeline starts the clock when the request arrives, so time spent waiting in the queue counts, and each model call and retry only gets the time that's left. A request that waited until less than 20% of its budget remained is refused with a 503 before any model is called.

In front of that, the API checks the pipeline's health endpoint, with a 1.5-second timeout and a 3-second cache shared by concurrent requests. When every worker thread is busy and 4 or more requests are queued, it returns 503 with Retry-After: 60 before claiming quota or checking spend limits. If the health check itself fails, requests go through, so a broken probe can't block every report. Liveness and readiness are separate endpoints, so a busy pipeline doesn't get its container restarted.

Deploys needed a guard too. If the server shipped ahead of the pipeline, a version mismatch would have regenerated every cached report anyone opened. The server now invalidates a cached report only when the live pipeline can already produce the newer version, and the deploy order and rollback steps are written down.

Infrastructure · Databases

Two database problems found before launch

A crash loop during deploys

One deploy restarted the server 11 times, each with EMAXCONNSESSION. During a rolling deploy two instances overlap, and one instance's default Prisma pool could fill Supabase's 15-client session pooler by itself. The pool is now capped at 6 whenever the connection string doesn't set a limit, leaving room for two instances and a migration, and startup retries migrate deploy with backoff.

A production schema that couldn't be rebuilt

Setting up staging, I replayed every migration into an empty database, and it failed twice. Seven tables and nine columns had been created by db push or hand-written SQL, never by a migration, so production couldn't have been rebuilt from source. I wrote two baseline migrations that recreate the original shapes idempotently, reset staging, replayed all 31 migrations from empty, and diffed the columns and indexes against production: 402 lines on each side, identical. The baselines were marked as applied in production, and a CI check now guards migration completeness.

Correctness · Billing

Quotas and billing that survive retries

A quota claim is a single SQL statement: an insert that, on conflict, increments the count only while it's below the limit, and returns the row. No row means no quota, and there's no gap between reading and writing. Label scans claim a batch inside a transaction with SELECT ... FOR UPDATE, and failures refund without going below zero. Writing it this way exposed a bug where the insert branch granted the first claim of every period even on a plan with a limit of zero.

The Stripe webhook verifies signatures and handles 9 event types. Each event ID is recorded before handling and deleted if the handler throws, so the route returns 500 and Stripe's retry runs cleanly, and stale events are ignored by timestamp. Refunds and disputes downgrade the account automatically. On the report and stack routes, four daily spend ceilings (per supplement, per free-tier supplement, per account, and global) are checked before quota is claimed.

Security

Closing an XXE path, then fixing the fix

PubMed returns XML, and Biopython's parser fetches the document type definitions it needs to read it, which left an XXE and server-side request forgery path. Turning entity resolution off wasn't an option, since the parser depends on those definitions, and swapping in a hardened XML library would have meant reimplementing its parsing. So I restricted where it can fetch from: nlm.nih.gov and its subdomains. The first version matched host names exactly, missed dtd.nlm.nih.gov, and broke every retrieval, which surfaced in reports as "No studies found". The allowlist now covers the subdomains, and a retrieval failure returns its own 503, so an outage shows up as an error message.

Elsewhere, the private pipeline refuses to start without its shared secret and compares it in constant time, CORS applies to /api only, and staging sits behind a signed-cookie gate.

Frontend

A report that re-rendered 60 times a second

Reports are model prose, so the client enriches them as they render, marking statistical notation and linking glossary terms to accessible popovers. Scrolling a long report used to re-render all of it every frame. Scroll progress lived in React state, a memo never engaged because of an inline arrow function, and counter-based keys remounted 94 spans and ran about 25,500 regular expressions per render. Moving progress to a subscription, memoizing the handlers, and deriving keys from content fixed it, and a CI check keeps the keys content-derived.

For search, 45 public routes are prerendered with headless Chromium.

Tooling

How changes get checked, and what isn't there yet

Every push to main or staging runs the client and server builds, typechecks, and 25 custom check scripts in GitHub Actions, and a failing check fails the build. Some enforce application invariants, like a CI check that found 8 async Express routes, checkout among them, that would hang on an error instead of returning one. Others enforce the design system. Changes go to the staging copy of each service before production.

There is no automated test suite yet, and no alerting. Request IDs are carried from Express into the Python service and logs redact secrets, which makes a failure traceable after the fact, but nothing pages anyone when one happens.
